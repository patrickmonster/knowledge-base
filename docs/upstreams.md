# 상위 프로젝트 (upstream)

여러 프로젝트가 함께 따르는 기준 자료(디자인 시안·디자인 시스템, 기획, 공통 API 명세 등)를 **상위 프로젝트 하나**에 두고, 서비스별 **하위 프로젝트**가 읽기 전용으로 참조하는 구조입니다. 디자인 전용이 아니라 어떤 기준 자료에도 쓸 수 있고, 하위 프로젝트 하나가 상위 프로젝트를 최대 5개(예: 디자인 + 기획)까지 따를 수 있습니다.

```
[상위: 디자인 시안]   [상위: 기획]        ← 기준 자료의 유일한 원본
      ▲  읽기 전용 · 이슈만     ▲
[하위: 서비스 A] [하위: 서비스 B] [하위: 서비스 C]
```

## 원칙

- **수정은 상위에서 한 번**: 하위 프로젝트의 작업에서 상위 문서를 고치지 않습니다. 문제가 있으면 상위 프로젝트에 이슈로 올리고, 상위 담당자가 고치면 모든 하위가 다음 작업에서 바로 최신 내용을 받습니다.
- **항상 최신 active**: 하위는 상위의 현재 active 문서를 참조합니다. 버전 고정은 없고, draft는 하위에 전달되지 않습니다.
- **연결은 상위가 승인**: 상위 문서를 누가 읽을지는 상위 소유자·관리자가 정합니다.
- 직접 연결만 따릅니다. 상위의 상위는 따라가지 않으며, 두 프로젝트가 서로를 따를 수 없습니다.

## 연결 절차

1. 상위 프로젝트 소유자가 웹 **프로젝트 → 상위 프로젝트** 화면 하단의 프로젝트 ID를 하위 프로젝트 소유자에게 전달합니다.
2. 하위 프로젝트 소유자·관리자가 같은 화면에서 그 ID로 **연결 요청**합니다(MCP `request_project_upstream`도 가능, 사용자가 요청할 때만).
3. 상위 프로젝트 소유자·관리자가 웹에서 **승인**합니다. 승인(`approve_project_upstream`)은 외부 사람에게 읽기 권한을 주는 일이라 웹 로그인 세션 전용이며 MCP 키로는 `FORBIDDEN`입니다. 양쪽을 모두 관리하는 사람이 웹에서 요청하면 바로 승인됩니다.
4. 연결 해제·요청 거절은 양쪽 소유자·관리자 누구나 할 수 있고(`remove_project_upstream`), 하위 참여자의 읽기 권한은 즉시 사라집니다.

## 하위 프로젝트 참여자가 할 수 있는 일

| 작업 | 가능 여부 |
| --- | --- |
| 상위 문서 읽기·목록·검색(`get_document`, `list_documents`, `search_knowledge`), 첨부 목록·다운로드 | 가능 (상위 참여 없이) |
| 상위 이슈·질의 읽기(`list_issues`, `get_issue`) | 가능 |
| 상위에 이슈·질의 올리기(`create_issue`) | 가능. 하위 프로젝트가 `origin_project_id`로 기록되고 웹 이슈 화면에 `하위 프로젝트 · 이름`으로 표시 |
| 내가 올린 상위 이슈에 댓글(`comment_issue`) | 가능 |
| 상위 문서 추가·수정·보관, `start_task`, 이슈 답변·해결 | 불가 (`NOT_FOUND`) |

- 상위에도 참여 중인 사람(예: 디자이너)은 원래 역할대로 상위를 편집합니다. 이 구조가 막는 것은 하위 프로젝트 참여 자격으로 상위를 고치는 일입니다.
- 특정 프로젝트로 제한된 MCP 키는 기존 규칙대로 그 프로젝트만 직접 호출합니다. 하위 프로젝트로 제한된 키도 `start_task`의 `upstream_sources`로는 상위 자료를 받습니다.
- 상위 이슈를 올릴 때 상위의 `task_id`·`todo_id`는 쓸 수 없습니다(상위 참여자만 볼 수 있는 항목). 하위 작업 내용은 본문에 적습니다.
- 여러 하위 프로젝트를 통해 같은 상위를 따르면 `create_issue`에 `from_project_id`를 지정해야 합니다.

## 작업 맥락 (`upstream_sources`)

하위 프로젝트에서 `start_task`·`get_task_context`를 호출하면 승인된 상위 프로젝트들을 작업 내용으로 검색해 결과를 `upstream_sources`(최대 4건, 각 결과에 `project_slug`·`project_name`)에 따로 담고, 연결된 상위 목록을 `upstream_projects`에 담습니다.

- active 문서만 대상이며 history는 제외합니다(상위의 작업 과정이 아니라 현재 기준이 필요).
- 발췌 예산(`excerpt_budget`)의 1/4을 상위 자료에 예약합니다. `related_project_ids`를 함께 쓰면 그 1/4도 따로 예약되어 이 프로젝트 자료는 절반을 씁니다.
- `related_project_ids`에 상위 프로젝트를 넣으면 `upstream_sources`와 중복되므로 무시합니다.
- 저장된 작업을 `get_task_run`으로 다시 읽을 때(웹 **진행 중 작업**의 **시작 자료 보기** 포함) `upstream_sources`는 지금도 승인된 상위 프로젝트의 자료만 남기고, 연결이 해제된 상위의 자료는 건수만 `upstream_hidden`에 담습니다.
- `guidance`는 상위 자료를 이 프로젝트 자료보다 우선하되, 상위 문서는 고치지 말고 `create_issue(project_id=<상위>, from_project_id=<이 프로젝트>)`로 보고하라고 안내합니다.

## 이슈 흐름

1. 하위 작업 중 시안과 구현이 맞지 않거나 시안에 문제가 있으면 상위 프로젝트에 이슈를 올립니다(관련 상위 문서는 `document_id`로 연결).
2. 상위 담당자가 이슈 화면에서 출처 하위 프로젝트를 확인하고(`list_issues`의 `origin_project_id` 필터), 상위 문서를 고친 뒤 이슈를 해결합니다.
3. 다음 `start_task`부터 모든 하위 프로젝트가 고친 내용을 `upstream_sources`로 받습니다.

## 데이터

마이그레이션 `042_project_upstreams`:

- `project_upstreams(project_id, upstream_project_id, status pending|approved, requested_by/at, approved_by/at)`. PK `(project_id, upstream_project_id)`, 자기 자신 금지, 양쪽 프로젝트 삭제 시 함께 삭제.
- `issues.origin_project_id`: 상위 이슈를 올린 하위 프로젝트(그 프로젝트가 삭제되면 비움).
