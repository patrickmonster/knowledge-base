# 팀 확산 기능 (2단계)

여러 사람과 여러 저장소가 같은 지식베이스를 쓰도록 돕는 기능입니다. `011_team_rollout` 마이그레이션이 필요합니다.

| 기능 | 위치 | 권한 |
| --- | --- | --- |
| 이슈 담당자 알림 (웹훅·Slack·이메일) | 웹 **이슈 · 질의** 아래 **담당자 알림** | 채널 관리: 프로젝트 소유자. 목록: 참여자 |
| 문서 관계 보기·편집 | 웹 **지식 문서**에서 문서를 펼친 뒤 **문서 관계** | 보기: 참여자. 연결·해제: 편집자 이상 |
| 문서 버전 비교 | 웹 **지식 문서** → 문서 펼치기 → **버전 비교** | 참여자 |
| 검토 대기 배지 | 사이드바 **검토 대기** 옆 숫자 (현재 프로젝트의 draft 수) | 참여자 |
| 공통 작업 영역 삭제·정리 | 웹 **이슈 · 질의** → 영역 표, MCP `delete_work_area` | 프로젝트 소유자 또는 영역 담당자 |
| 다른 저장소에 작업 규칙 적용 | 저장소 등록 `add_project_repository`(소유자·관리자) + 사용자 수준 MCP 연결. 지침 파일은 선택(`get_agents_template`) | 소유자·관리자 |
| 프로젝트 내보내기·가져오기 | 웹 **프로젝트** → **백업 · 이전 · AGENTS.md** | 내보내기: 참여자. 가져오기: 프로젝트 소유자 |

## 이슈 담당자 알림

질의·이슈가 바뀌면 같은 트랜잭션에서 알림 대기열(`notification_outbox`)에 쌓고, 서버의 백그라운드 작업이 프로젝트의 알림 채널로 보냅니다. 변경이 취소되면 알림도 남지 않습니다.

| 이벤트 | 언제 | 받는 사람 |
| --- | --- | --- |
| `issue_assigned` | 담당자를 지정해 등록하거나 담당자를 바꿀 때 | 새 담당자 |
| `issue_answered` | 답변 등록·수정 | 질의자 |
| `issue_commented` | 댓글 | 질의자, 담당자 |
| `issue_status` | 해결·닫기·다시 열기 | 질의자, 담당자 |
| `recheck_digest` | 정해진 주기에 기한 지난 재확인 문서가 있을 때(옵트인) | 채널(이메일은 각 담당자) |

- 변경한 본인에게는 보내지 않습니다. 받을 사람이 없으면 알림을 만들지 않습니다.
- 알림에는 프로젝트·제목·종류·상태·영역·작업 보류 여부·이름과 웹 화면 링크(`/#issues`)만 담습니다. **질의 본문과 답변은 보내지 않습니다.**
- 채널 종류
  - **Slack**: incoming webhook URL(`https://hooks.slack.com/...`). `{"text": "..."}`로 보냅니다.
  - **웹훅**: 임의 HTTPS 주소에 JSON을 POST 합니다. 헤더 `X-KB-Event`(이벤트), `X-KB-Delivery`(재전송 시에도 같은 ID)로 중복을 거를 수 있습니다.
    - **Discord**: 주소가 Discord 웹훅(`https://discord.com/api/webhooks/…`, `discordapp.com`·`ptb.`·`canary.` 포함)이면 자동으로 Discord 형식(`{"content": "...", "username": "knowledge-base"}`)으로 보냅니다. 메시지는 2,000자에서 자르고, 제목에 `@everyone` 등이 있어도 멘션되지 않도록 `allowed_mentions`를 비웁니다. Discord 채널 설정 → 연동 → 웹후크에서 만든 URL을 종류 **웹훅**으로 등록하면 됩니다.
  - **이메일**: 받는 사람의 계정 이메일로 보냅니다. 서버에 `SMTP_HOST`, `SMTP_FROM`(필요하면 `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`)을 설정해야 하며, 없으면 `SMTP_NOT_CONFIGURED`로 실패 처리됩니다.
- 채널 주소에는 비밀 값이 들어 있을 수 있어 저장 후에는 호스트와 끝 4자리만 보여 주고, 감사 로그에도 복사하지 않습니다. 수정할 때 주소를 비워 두면 기존 주소를 유지합니다.
- 내부망 보호: 접속 시점에 실제 IP를 확인해 루프백·사설·링크 로컬·CGNAT 주소로는 보내지 않고(`BLOCKED_ADDRESS`), 리디렉션을 따라가지 않으며, 프록시를 쓰지 않습니다.
- 재시도: 연결 실패·429·5xx는 1, 2, 4, 8, 16분 간격으로 최대 6번 보냅니다. 그 밖의 4xx·3xx와 설정 오류는 바로 실패 처리합니다. 실패 사유는 코드만 남깁니다.
- **재확인 요약**: 이벤트 `recheck_digest`를 고른 채널은 기한이 지난 문서 요약을 주기적으로 받습니다(기본 매주 월요일 9시, `RECHECK_DIGEST_SCHEDULE`·`RECHECK_DIGEST_HOUR`로 조정). 기본 이벤트에는 들어 있지 않습니다. 같은 주기에 한 번만 보내고, 기한 지난 문서가 없으면 보내지 않습니다. 내용과 받는 사람은 [지식 품질 안내](knowledge-quality.md#재확인-요약-발송)를 봅니다. `032_recheck_digest_runs` 마이그레이션이 필요합니다.
- 채널 관리는 사람의 결정입니다. 알림 도구(`list_notification_channels`, `set_notification_channel`, `test_notification_channel`)는 웹 화면 전용이며 MCP 키로는 호출할 수 없습니다.
- `NOTIFICATIONS_ENABLED=false`면 대기열에만 쌓고 보내지 않습니다. 발송 기록은 30일 뒤 지웁니다.

## 문서 관계 보기·편집

`get_document_links`/`link_documents`/`unlink_documents`를 웹에서 사용합니다. 펼친 문서의 시점에서 “이 문서가 대체한 이전 문서”, “이 문서를 대체한 새 문서”, “이 작업 이력이 수행한 결정·기획”, “이 문서를 수행한 작업 이력”, “관련 문서”로 묶어 보여 줍니다. 상대 문서는 최근 문서 100개 목록에서 고르거나 문서 ID를 붙여 넣습니다. 규칙(같은 종류끼리만 대체, 작업 이력 → 결정·기획만 수행 등)은 서버가 검사합니다.

## 문서 버전 비교

`get_document_history`와 `get_document(revision)`으로 두 버전을 불러와 브라우저에서 줄 단위 차이(Myers diff)를 계산합니다. 제목·종류·상태·태그·출처 URL 변경은 표로, 본문은 변경 주변 3줄을 포함해 보여 주고, 두 버전 사이의 변경 사유를 함께 표시합니다. 변경이 3,000줄을 넘으면 전체 삭제·추가로 단순하게 보여 줍니다.

## 검토 대기 배지

`count_documents(status: draft)`로 현재 프로젝트의 draft 수를 세어 사이드바에 표시합니다. 프로젝트를 바꾸거나 검토를 마치면 갱신하고, 화면이 보이는 동안 1분마다 다시 확인합니다. `count_documents`는 MCP에서도 쓸 수 있습니다.

## 공통 작업 영역 삭제·정리

- `list_work_areas`의 `owner_active`가 `false`면 담당자가 프로젝트를 떠났거나 조회자가 되었거나 비활성화된 영역입니다. 웹 영역 표에 “담당자 확인 필요”로 표시됩니다. 담당자를 바꾸거나 삭제합니다.
- `delete_work_area(project_id, area_id, move_to_area_id?)`: 질의·이슈는 지우지 않습니다. `move_to_area_id`가 있으면 그 영역으로 옮기고, 없으면 영역 없이 남깁니다(담당자는 유지). 결과에 옮긴 건수(`moved_issues`)와 영역 없이 남은 건수(`detached_issues`)가 나옵니다.

## 다른 저장소에 작업 규칙 적용

대상 저장소에는 아무 파일도 두지 않습니다. 서버 주소·프로젝트 이름·지침 파일이 저장소에 남으면 이 서버를 쓴다는 흔적(워터마크)이 되어 공격 대상 식별이 쉬워지기 때문입니다. 저장소와 프로젝트의 연결은 서버에만 둡니다.

1. 소유자·관리자가 대상 저장소의 git remote를 프로젝트에 등록합니다(`add_project_repository`).
2. 그 저장소에서 쓰는 AI 도구에 이 서버의 MCP(`/mcp`)와 해당 프로젝트에 접근 가능한 키를 **사용자 수준 설정**으로 연결합니다(예: `claude mcp add --scope user`). 커밋되는 `.mcp.json` 같은 프로젝트 설정에는 두지 않습니다.
3. AI는 연결 시 서버 지침(`internal/kb/instructions.go`)을 받아, 연결된 knowledge 서버마다 `resolve_project(git remote)`를 부릅니다. `matched: true`인 서버의 프로젝트로 `start_task`·`finish_task`를 하고 응답에 함께 온 작업 규칙(`rules`)을 따르며, `matched: false`인 서버는 사용자에게 묻지 않고 건너뜁니다. 서버가 여러 대 연결돼 있어도 등록된 서버만 기록하고, 어디에도 등록되지 않은 저장소에서는 knowledge 없이 평소대로 작업합니다.

웹 **백업 · 이전** 화면과 `get_agents_template`는 같은 지침을 서버·프로젝트 이름 없이 Markdown으로 줍니다. 선택 사항이며, 쓰려면 사용자 수준 지침(`~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` 등)에 넣고 저장소에는 커밋하지 않습니다.

## 프로젝트 내보내기·가져오기

| 형식 | 내용 | 용도 |
| --- | --- | --- |
| JSON (버전 기록 포함) | 프로젝트 정보, 모든 문서와 전체 버전 스냅샷·사유, 문서 관계, 할 일, 공통 작업 영역, 이슈·질의와 댓글 | 백업 보조, 감사 |
| JSON (현재 버전만) | 위에서 버전 기록 제외 | 이전, 가벼운 백업 |
| Markdown (zip) | `documents/<종류>/<제목>-<ID 앞 8자>.md`(JSON 표기 front matter), `issues/*.md`, 할 일 표 `todos.md`, 색인 `README.md`, 가져오기용 `export.json` | 사람이 읽기, Git 보관, 이전 |

- 웹 세션 전용 HTTP 엔드포인트입니다: `GET /api/projects/{id}/export?format=json|markdown[&revisions=false]`, `POST /api/projects/{id}/import`(`application/json` 또는 `application/zip`), `GET /api/projects/{id}/agents.md`. 감사 로그에 `export_project`·`import_project`로 남습니다.
- 내보내기는 문서 5,000개까지, 가져오기는 32 MiB·문서 5,000개까지입니다. 첨부 파일 원본은 포함하지 않습니다.
- 가져오기는 **기존 프로젝트**에 문서, 관계, 할 일을 새로 만듭니다(소유자만, 한 트랜잭션). 각 문서는 현재 내용으로 첫 버전을 만들고 작성자는 가져온 사람, 버전 사유에 원본 프로젝트·문서 ID·버전을 남깁니다. 상태(draft·active·archived)는 유지합니다.
- 원본 문서 ID를 `documents.imported_from`에 저장해 같은 파일을 다시 가져오면 이미 가져온 문서는 건너뜁니다. 원본 프로젝트에 다시 가져와도 원본 문서를 알아보고 건너뜁니다.
- 할 일은 제목·내용·상태·우선순위·분류·진행률·마감일·칸 안 순서·완료 시각을 그대로 가져옵니다. 작성자는 가져온 사람이 됩니다. 원본 서버에 묶인 정보는 가져오지 않고 건수를 경고로 알려 줍니다: 담당자(원본 서버 사용자)는 비우고, 연결된 작업·PR(작업 기록은 내보내지 않음)과 질의(가져오지 않음) 연결은 끊깁니다. 내보낸 파일의 `todos`에는 담당자 이름, 연결 작업·질의 수, PR 목록이 참고용으로 남습니다.
- 원본 할 일 ID를 `todos.imported_from`에 저장해(`031_todo_import` 마이그레이션) 다시 가져오면 이미 가져온 할 일은 건너뜁니다. 건너뛴 할 일은 덮어쓰지 않으므로 가져온 뒤 고친 내용이 유지됩니다. 프로젝트당 5,000건 한도를 넘으면 전체를 되돌립니다. 할 일이 없는 예전 내보내기 파일도 그대로 가져올 수 있습니다.
- 공통 작업 영역·이슈는 원본 서버의 사용자 ID를 참조하므로 가져오지 않고 건수만 알려 줍니다. 이전 버전 기록도 가져오지 않습니다.
- 문서나 할 일 하나라도 형식이 잘못되면 전체를 되돌리고 어느 항목이 문제인지 알려 줍니다. 가져온 문서는 임베딩 대기열에 들어가므로 의미 검색 준비까지 시간이 걸립니다.
- 내보내기는 정기 DB 백업을 대신하지 않습니다.
